# 故障与业务不变量验证矩阵

> 这是待实现的验收规范，不是已通过的测试报告。当前仓库没有运行服务、自动化业务测试或真实资金验证结果。

## 1. 验证方式

未来实现应使用隔离环境和可编排的模拟渠道，覆盖响应丢失、重复通知、乱序事件、数据库提交后崩溃、消息重放与依赖不可用。

每个用例保存：输入身份和金额、故障注入位置、重启前后持久化状态、外部模拟操作次数、账务分录、资金占用及差错记录。

“没有报错”不是验收条件；必须断言具体业务不变量。模拟测试通过后，真实渠道能力仍需在授权测试环境单独验证。

## 2. 收款与状态收敛

| 编号 | 场景与故障点 | 必须成立的断言 |
| --- | --- | --- |
| P01 | 同商户、同操作键、同参数并发提交 | 只产生一个支付意图；后续请求返回同一业务身份 |
| P02 | 同键改变金额、币种或收款主体 | 明确拒绝参数冲突，不修改原操作 |
| P03 | 渠道已受理但尚未扣款 | 保持处理中，不提前发布支付成功事实 |
| P04 | 授权成功但未捕获 | 保留授权事实，不将授权自动解释为收款成功 |
| P05 | 渠道扣款成功、响应丢失 | 尝试进入未知或待核实路径，不创建新扣款 |
| P06 | 查单暂时无记录，之后返回成功 | 原操作收敛成功；期间不开放跨渠道重试 |
| P07 | 明确失败且渠道保证不会再扣款 | 才可依据业务决策创建新尝试 |
| P08 | 取消请求仅被受理，捕获仍在途 | 不提前释放收款风险，继续核查最终效果 |
| P09 | 支付成功后发生全额退款 | 原收款事实保留，退款独立表达 |
| P10 | 终态后收到相反资金证据 | 保存证据并建立差错，不静默丢弃或覆盖历史 |

关联设计：[支付生命周期](payment-lifecycle.md) 的 L1—L7 状态与证据规则。

## 3. 通知、消息与账务幂等

| 编号 | 场景与故障点 | 必须成立的断言 |
| --- | --- | --- |
| M01 | 相同事件 ID 重放 | 不重复确认资金事实、不重复产生账务效果 |
| M02 | 不同事件 ID 表达同一成功事实 | 业务唯一约束仍能防止重复入账 |
| M03 | 处理中通知晚于成功通知到达 | 成功投影不回退为处理中 |
| M04 | 同事件 ID 对应不同载荷摘要 | 隔离冲突并告警，不按普通重复忽略 |
| M05 | 验签失败或商户、币种不匹配 | 不产生支付成功事实，保留脱敏审计 |
| M06 | 业务状态与 Outbox 之间进程崩溃 | 事务整体提交或整体不存在，不出现无任务的已提交事实 |
| M07 | 发布成功后、进度标记前崩溃 | 同事件可重发，消费者只产生一次本地效果 |
| M08 | Inbox 与账务效果同事务提交后丢响应 | 重投返回既有结果，不新增第二份原始凭证 |
| M09 | 凭证已提交但本地记账确认丢失 | 按原指令查询，恢复记账状态而非再次记账 |
| M10 | 渠道成功但账本持续不可用 | 保留成功事实、待记账任务和门禁，不改成支付失败 |

关联设计：[一致性与恢复](consistency-and-recovery.md)。

## 4. 账务、退款与并发额度

| 编号 | 场景与故障点 | 必须成立的断言 |
| --- | --- | --- |
| L01 | 同一凭证包含多个币种分录 | 每币种分别平衡，不通过数值相等混币配平 |
| L02 | 余额 100，两笔并发操作各申请 80 | 禁止透支用途下至多一笔成功，另一笔无资金效果 |
| L03 | 原付 100，成功退 70、预留 20，再申请 20 | 新退款被拒绝，不超可退额度 |
| L04 | 同一退款的确认与释放并发 | 预留只终结一次，状态和累计金额一致 |
| L05 | 退款超时、查询不明、任务截止 | 保留未知与占额，不自动释放后再次退款 |
| L06 | 退款成功通知之后又出现失败或退回 | 追加证据与调整，不删除原成功历史 |
| L07 | 商户甲请求使用商户乙账户 | 权限拒绝，不产生跨商户资金变化 |
| L08 | 投影落后于最近出款 | 资金批准不使用过期投影，重建后与源账本一致 |
| L09 | 跨分片转移在源确认、目标开放之间中断 | 不形成双份可支用余额，未知占额持续可恢复 |
| L10 | 修账审批回调重复 | 同一修正动作只执行一次，原凭证和关联保留 |

编号与[账本不变量](ledger.md#4-十个可验证不变量)对应；这里描述故障输入和验收断言，不宣称约束已经实现。

## 5. 清结算与对账

| 编号 | 场景与故障点 | 必须成立的断言 |
| --- | --- | --- |
| S01 | 同一应结明细被两个批次尝试消费 | 有效归属唯一，不重复形成应付或付款 |
| S02 | 出款超时但银行可能已扣账 | 保留原指令和占额，不换单号重复付款 |
| S03 | 渠道标记已结算但商户未到账 | 不将渠道状态等同于商户收款完成 |
| S04 | 100 收款、20 退款、2 渠道费同批 | 在限定口径下净额为 78，银行到账仍待证据 |
| S05 | 退款属于下一结算批次 | 两批分别解释，不强迫当前批匹配 78 |
| S06 | 同一报告重复导入或修订重发 | 文件身份与业务明细分别去重，不重复入账 |
| S07 | 报告缺页、空文件或未到文件 | 区分数据缺失与零交易，不宣称全量核对完成 |
| S08 | 漏一笔 100、多一笔 100 | 汇总可能相等，但逐笔差错不能关闭 |
| S09 | 一笔银行流水匹配多笔结算明细 | 保存分配关系与剩余额，同一流水不可重复消费 |
| S10 | 出款成功后资金退回 | 追加退回事实和修正凭证，重新评估应付与资格 |

关联设计：[清分、结算与对账](settlement-and-reconciliation.md)。

## 6. 恢复与安全控制

| 编号 | 场景 | 必须成立的断言 |
| --- | --- | --- |
| R01 | 恢复任务租约过期，但旧请求仍可能执行 | 新任务复用原身份，不以租约失效证明外部失败 |
| R02 | 灾备恢复遗漏去重历史 | 暂停受影响重放，补齐证据前不开放重复执行 |
| R03 | 旧地域写入者在切换后返回 | 本地权威隔离有效，外部迟到效果进入核查 |
| R04 | 收款账户变更或人工修账缺少审批 | 拒绝敏感操作，记录授权失败原因 |
| R05 | 日志采集遇到支付凭证或密钥 | 敏感内容不进入公开日志与指标标签 |

## 7. 通过条件与证据

未来每个阶段的通过条件应包括：

- 所有适用用例有可复现输入和自动化断言，而不是只有演示截图。
- 故障注入后重启，仍能按原身份找到操作、证据和资金占用。
- 金额、币种、商户、账套及结算归属均可追溯。
- 重复执行不会增加非预期资金效果；未知结果不会被伪造成失败。
- 对账差异能解释、能分派、能复核，不能靠修改历史强行相等。

当前状态：阶段 1—3 的 P、M、L、S 适用用例与阶段 4 的 R01—R05 已有本地自动化断言；容量压测、真实灾备演练、真实安全/合规审计与真实渠道验证仍未执行。本矩阵用于指导后续开发，不应被 README 或发布说明描述为已具备生产级能力。
