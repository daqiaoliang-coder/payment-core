# 一致性、幂等与故障恢复

> 状态：设计草案，未实现。日期：2026-10-30。
> 本文是通用商户即时收款的参考设计，不承诺金融生产可用、端到端 exactly-once 或未经测试的性能。

## 1. 保证范围与前提

- **设计建议**：以下事务、唯一约束、任务与业务门禁是后续实现要求，不是现有能力。
- **产品事实**：引用的渠道、AWS、Kafka 文档只证明各产品自身的条件化行为。
- 后续可优先采用模块化单体，但当前没有实现，不能声称模块已共享数据库事务。
- 本文假设选用支持原子事务、持久化和唯一约束的数据库；实际隔离级别仍需验证。
- 本地事务只能约束同一数据库内的写入，不能包含渠道扣款、消息系统或另一数据库的提交。
- 目标是“至少一次传递 + 可识别的重复 + 可恢复的业务效果”，不是宣称全链路只执行一次。
- 支付成功、记账完成、允许履约、允许结算必须分开表示；后两者是业务门禁。
- 对象、证据和状态定义以[支付生命周期](payment-lifecycle.md)为准。

## 2. 事务边界总览

| 边界 | 同一事务内必须包含 | 明确不包含 |
| --- | --- | --- |
| T1 收款受理 | 商户幂等绑定、支付单、尝试与操作身份、发送意图 outbox | 渠道调用 |
| T2 发送领取 | 执行租约或版本、发送意图标记、原渠道键与参数引用 | 网络发送及渠道受理 |
| T3 证据接收 | 验证后的通知或查询证据、来源身份、待处理状态 | 对外业务效果和远端记账 |
| T4 事实确认 | 处理去重标记、资金事实、支付投影、待记账标记、业务 outbox | 消息发布及外部账本调用 |
| T5 消费落地 | consumer inbox、该消费者的本地业务效果、必要的下游 outbox | 其他数据库和渠道效果 |
| T6 退款受理 | 原收款额度锁定、退款幂等绑定、额度预留、退款操作、发送 outbox | 实际退款 |
| T7 退款结论 | 退款证据与事实、预留转实退或有证据释放、结果 outbox | 消息系统确认 |

- 事务名是文档标记，不是已实现接口；T3 与 T4 可在满足可靠证据留存时合并。
- 各边界内出现多个表不影响原子性，但必须确实位于同一数据库事务中。
- 接收记录与处理标记分离：已接收不等于已完成，不能提前写“已消费”跳过后续效果。
- 外部系统返回后，本地事务失败不会撤销外部效果，必须回到证据核查和幂等恢复路径。

## 3. 业务幂等与参数绑定

- 商户请求建议以“商户 + 操作类别 + 约定命名空间 + 幂等键”建立数据库唯一约束。
- 保存规范化参数及摘要，包括金额、币种、收款主体、原操作引用和影响执行的选项。
- 规范化规则应版本化，保留可审计的参数表示，不能只凭不明来源的摘要判断等价。
- 同键同参数返回已有操作或当前结果；同键异参明确拒绝，不悄悄修改已有操作。
- 并发请求以数据库唯一约束裁决，冲突方读取已提交记录；不能只靠“先查后写”。
- 商户订单引用还需业务级约束，避免调用方换键后对同一未决收款意图再次扣款。
- 尝试的渠道账户、环境、区域、操作类别和渠道键应不可变，不能在重试时重新路由。
- 渠道引用的唯一性必须按其真实作用域定义，不把不同账户的裸引用当成同一交易。
- 资金事实去重键应包含原操作与渠道事实身份，区分真实的多次捕获、退款和资金调整。
- 同一事实对应的记账指令应具有稳定身份，由账务域唯一约束避免重复产生账务效果。
- 所有冲突均应校验参数一致；重复不代表可以忽略金额、币种或载荷变化。
- 幂等响应缓存可过期，但业务身份、资金事实和仍可能重放的去重信息不能随缓存一并删除。
- 保留策略须覆盖渠道重试、消息重放、备份恢复及人工补单窗口，具体期限另行确定。

## 4. 渠道幂等不是永久通用契约

| 产品事实 | 来源 | 对本设计的限制 |
| --- | --- | --- |
| Stripe 的键至少保留 24 小时后可被清理 | [Idempotent requests](https://docs.stripe.com/api/idempotent_requests) | 不能把原键理解为无限期防重 |
| Stripe 开始执行后会保存首次结果，包括 `500` 响应 | [Idempotent requests](https://docs.stripe.com/api/idempotent_requests) | 同键重试可能持续返回同一错误，不能由此断定未扣款 |
| Adyen 幂等作用域为 company，保留窗口为 7–14 天 | [API idempotency](https://docs.adyen.com/development-resources/api-idempotency) | 本地应固定作用域，不能依赖最长窗口无限重放 |
| Adyen 不在不同区域端点之间检查重复请求 | [API idempotency](https://docs.adyen.com/development-resources/api-idempotency) | 原键跨区域发送也可能产生重复效果 |

- **设计建议**：渠道适配配置应记录幂等支持范围、操作类型、保留窗口及查询能力。
- Stripe 参数校验失败或并发冲突等未开始执行的情形，与已缓存执行结果应分别处理。
- 安全重发要求原身份、同参数、同作用域，并处于已确认有效的幂等保护条件内。
- 超出保护窗口、缺少查询能力或跨区域迁移时，应进入核查与升级，不自动换新键。
- `UNKNOWN` 时不得自动切换渠道、新建尝试或新建退款来“提高成功率”。

## 5. DB 业务写入与 outbox 同事务

1. T1 或 T4 在写业务记录时，同时插入稳定 `event_id` 的 outbox 记录。
2. outbox 保存聚合身份、版本、事件类型、模式版本及最小必要业务载荷。
3. 两者一起提交或回滚，避免“业务已提交但通知永远没有产生”的双写缺口。
4. 发布器领取已提交的 outbox，向消息系统发布，等待约定的发布确认。
5. 发布确认后再更新本地发送进度；领取状态或租约到期不能冒充发布成功。
6. 未获得确认时保留可重发状态，采用相同事件 ID，不为每次投递生成新事件。

- 发布成功到本地标记成功之间存在窗口：此时崩溃会造成重复发布，而不是安全跳过。
- 若先标记成功再发布，崩溃可能丢事件，因此禁止这一顺序。
- 消息确认级别及持久性由所选系统配置决定；outbox 本身不证明消息永不丢失。
- 业务顺序需要聚合版本或同聚合串行策略；不能假设全局 FIFO 或跨主题顺序。
- 死信、归档和重放必须保留原事件身份，不能把投递失败改写为支付失败。
- **产品事实**：AWS 的 transactional outbox 模式解决数据库更新与通知之间的双写问题，并要求应对重复消息。
- 来源：[AWS Transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)。

## 6. Consumer inbox 与本地 effect 同事务

1. 消费者收到事件后开始 T5，尝试插入“消费者身份 + 来源 + 事件 ID”的 inbox 唯一记录。
2. 若已存在完成记录，校验载荷一致后跳过效果并确认消息；若冲突事务未提交则等待或重试。
3. 首次处理时，在同一事务内校验业务状态、执行本地 effect，并写必要的下游 outbox。
4. 本地 effect 可以是记账指令落地、订单投影更新或商户通知任务创建，而不是远端请求完成。
5. inbox 与 effect 一起提交后才确认消息或提交消费位点；事务失败则两者均回滚。
6. 提交成功但确认消息前崩溃时，重投会命中 inbox，避免再次执行同一数据库效果。

- 若 inbox 与 effect 分属不同数据库，这一原子性不成立，应由效果所属方另建幂等入口。
- 两个不同事件 ID 可能表达同一资金事实，因此 effect 仍需业务唯一约束，不能只靠 inbox。
- 不可解释的同 ID 异载荷应隔离；缺前置事实的乱序事件应持久化等待，不强行覆盖终态。
- 多事件处理与位点提交须避免跳过尚未落地的前序消息，具体规则依消费协议设计。
- 商户 Webhook 等外部效果通过本地任务再发送，接收方仍需业务幂等，不能纳入 T5。
- **产品事实**：Kafka 幂等生产者和事务有特定的日志写入及流处理边界；外部目标需要协作。
- Kafka 的事务能力不自动覆盖业务数据库或支付渠道，不构成本项目端到端 exactly-once 保证。
- 来源：[Kafka 4.1 Design](https://kafka.apache.org/41/design/design/)。

## 7. 渠道发送与查询恢复

1. T1 必须先持久化 `attempt_id`、`operation_id`、渠道键、固定端点及绑定参数，才允许发送。
2. T2 提交领取版本与发送意图，把尝试置于 `SUBMITTED`；不在数据库锁内等待网络响应。
3. 发送器使用已持久化的原身份执行请求，不在内存临时生成新键后直接发送。
4. 响应可信且字段完整时，经 T3/T4 保存证据和事实；响应受理则保留处理中。
5. 请求超时、连接断开或响应落库前崩溃时，将未决尝试纳入 `UNKNOWN` 核查。
6. 优先按渠道引用、原商户引用或渠道提供的查询方式找回结果；不是所有渠道都可按幂等键查询。
7. 查询确认成功则补录原操作的成功事实；确认处理中则继续等待，不再发起新收款。
8. 仅在原幂等保护条件明确有效时，才允许按渠道契约重发同一请求。
9. 查询无记录但可能延迟可见时继续核查；不能把“暂未查到”视作允许换渠道的依据。
10. 只有确认前次不能再扣款并封闭旧发送任务，才可经业务决策创建新尝试。

- 典型场景：渠道扣款成功，发送进程立即崩溃；本地不能凭缺少成功记录再次扣款。
- 恢复入口应覆盖积压 `SUBMITTED`，而不只扫描已有 `UNKNOWN` 的记录。
- 租约失效不能撤销已发出的 HTTP 请求；旧工作者仍可能在渠道侧产生效果。
- 新工作者必须复用原幂等身份；本地版本或 fencing 只能保护本地写入，不能假定渠道支持它。
- 人工补单也走相同证据和唯一约束，不提供直接“强改成功/失败”的绕过路径。

## 8. 同步与异步记账的业务门禁

| 路径 | 推荐本地边界 | 对外可见结果 | 履约与结算门禁 |
| --- | --- | --- | --- |
| 同步、同库记账 | 先可靠保存渠道事实，再把凭证、记账状态和放行事件放在一个事务中 | 渠道成功可见；完整完成需等待记账事务 | 记账提交前不发布放行事件 |
| 同步、远端账本 | 本地事实事务后，以稳定指令调用账本，再核对账本结果 | 响应超时则记账待核实，不否认支付成功 | 没有可信记账确认不得放行 |
| 异步记账 | T4 保存成功事实、待记账状态和 outbox；账务消费者幂等落地 | 明确展示支付成功、记账待完成 | 按预先约定策略独立评估，不因消息已发送而放行 |

- “同步”描述对外完成前等待记账，不意味着渠道调用与账务处在一个原子事务。
- 账务暂不可用时，应保留支付成功事实与 `PENDING_POSTING` 等独立记账状态，不改为支付失败。
- 若同库记账步骤失败，已保存的证据和成功事实仍应可恢复；不得仅依赖内存响应重建。
- 异步路径的保守默认是记账完成后才放行履约；若要提前履约，须另有明确的业务授权与损失承担规则。
- 所有路径下，可结算还需满足账务、差错与结算规则；支付成功或通知已送达都不是充分条件。
- 账本超时也属于外部未知结果，应按原记账指令查询或幂等重试，不能生成第二条等价指令。
- 对商户发送“支付成功”事实通知与发送“允许履约”指令应分开命名，避免消费者误用。
- 已记账但本地确认丢失时，以原指令取得账务结果，补齐投影和门禁，不重复记账。

## 9. 退款额度原子预留

- 可退基数来自已确认且允许退款的原扣款或捕获金额，同币种计算，不从订单显示金额猜测。
- 在单一退款池中，可用额度为可退基数减已确认退款、在途预留及尚未重叠计入的限制额度。
- 拒付等限制与退款可能重叠，无法可靠归属时冻结并核查，不按两个简单累计数重复扣减。
- T6 锁定额度聚合行或使用等价的原子条件更新，同时校验可用额度和预留退款金额。
- 预留、退款身份、商户幂等绑定及发送 outbox 同事务提交；不能先发送再补额度记录。
- 并发退款必须由同一原子额度约束裁决；“读剩余额度后分别插入退款”会超退。
- 同键重试返回原退款，不重复预留；不同键仍受累计额度约束。
- 退款确认完成时，在 T7 把预留转换为已退款金额，不能释放后再异步增加实退累计。
- 只有确认未执行且不能再执行的失败或取消，才在 T7 释放相应预留。
- `UNKNOWN`、查询无记录、超过任务截止或渠道仅受理，都不能自动释放预留。
- Adyen `REFUND success=true` 仅代表校验通过，不能据此套用通用的最终退款记账或释放规则。
- 来源：[Adyen Refund](https://docs.adyen.com/online-payments/refund)。
- 退款后迟到失败、资金退回或拒付证据进入独立差错与调整流程，不直接清空历史累计。
- 人工释放额度必须附确认依据和授权记录；不能通过结束恢复任务间接释放资金额度。

## 10. 崩溃位置与恢复表

| 崩溃位置 | 可能已经发生什么 | 恢复依据与动作 | 禁止做法 |
| --- | --- | --- | --- |
| T1 提交前 | 无已提交本地意图；设计上不应有发送 | 商户同键重试，重新进行唯一性裁决 | 先调用渠道再补身份 |
| T1 提交后、T2 前 | 意图已落库，尚待领取 | 扫描 outbox，使用原操作身份 | 创建第二张支付单 |
| T2 提交后、实际发送前 | 本地无法仅据标记证明已发送 | 原身份核查，必要时在有效幂等条件下重发 | 把 `SUBMITTED` 当作已成功 |
| 发送成功、响应保存前 | 渠道可能已经扣款 | 扫描未决尝试，查询原交易并补录证据 | 新键或换渠道再扣一次 |
| T3 已提交、T4 前 | 证据可靠保存，业务投影未更新 | 重放待处理证据，执行事实唯一约束 | 因已应答通知而跳过处理 |
| T4 提交后、发布前 | 成功事实及 outbox 已存在 | 发布器重扫同事件 | 把业务状态回滚为未支付 |
| 发布成功、标记前 | 消息可能已经被消费 | 重发同事件，由消费者幂等处理 | 声称发布恰好一次 |
| T5 effect 写入但提交前 | 本地事务应整体回滚 | 消息重投并重做完整事务 | 提前提交消费位点 |
| T5 提交后、消息确认前 | effect 与 inbox 都已持久化 | 重投命中 inbox，校验后确认 | 再执行一次业务效果 |
| 账本成功、本地确认前 | 凭证可能已生成 | 按原指令查询账本，补记账状态 | 生成新记账指令 |
| T6 提交后、退款结果丢失 | 预留存在，渠道可能已退款 | 保持预留，按原退款操作查询 | 超时释放后允许再次退款 |
| T7 提交后、通知前 | 额度和退款事实已经一致更新 | 重发结果 outbox，不重做额度变更 | 按通知次数累加已退款 |
| 恢复任务领取后崩溃 | 租约过期，外部请求可能仍在途 | 重新领取同任务并复核原操作 | 以租约过期证明外部未执行 |

## 11. 持久化恢复任务与升级

- 任务记录应包含对象身份、任务类型、未决原因、最近证据和固定渠道作用域。
- 保存 `attempt_count`、`next_run_at`、`deadline_at`、错误分类、租约及版本，重启后可继续。
- 采用有上限的指数退避和抖动，并遵循渠道限流建议；具体参数需按接入契约验证。
- 区分临时网络错误、限流、认证错误、参数错误和证据冲突，不把所有错误无限快速重试。
- 同一操作同一恢复目的应有唯一任务约束；新的通知可唤醒任务，但不能复制资金操作。
- 扫描范围包括未决发送、待处理证据、未发布 outbox、待记账、退款预留和隔离事件。
- 截止时间只触发告警、人工核查或限制新业务，不得伪造 `FAILED` 或释放未知退款额度。
- 达到最大自动重试次数后保留任务、身份与证据；自动执行可暂停，业务未知状态不能被删除。
- 人工处理记录操作人、依据、时间和审批信息；差错关闭应有可审计的实际处理结论。
- 迟到相反证据必须追加保存并重开差错评估，不能因任务已结束或状态已终态而丢弃。
- 备份恢复或消息历史重放前，应核对去重记录保留范围；数据库回滚不等于渠道资金回滚。
- 观察指标应覆盖未知存量及最老年龄、待记账金额、退款预留年龄、outbox 积压和冲突数。
- 恢复目标、告警阈值和吞吐量仍待实现验证；本文不把设计表格当作压测或故障演练结果。
