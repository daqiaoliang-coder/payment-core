# 可靠性、安全与灾备设计

> 参考设计，未实现、未压测、未开展安全审计或灾备演练。本文不承诺生产可用，不规定通用 TPS、RPO 或 RTO。

## 1. 正确性优先于表面成功率

接口成功率高，不代表没有重复扣款。超时快速返回失败、丢弃迟到通知或清空待记账队列，可能让系统看起来更稳定，却掩盖真实资金问题。

设计目标分为三层：

1. 资金安全：不重复产生非预期扣款、退款、记账或出款。
2. 可恢复性：在未知、崩溃、积压与部分失败后，能够找回原操作和证据。
3. 服务可用性：在不破坏前两项的前提下，保持受理、查询和运营能力。

不同业务门禁应有不同降级策略；不能把所有故障统一转换为“返回失败并重新下单”。

## 2. 故障隔离与降级

| 依赖故障 | 可继续的能力 | 需要限制的能力 | 不应采取的动作 |
| --- | --- | --- | --- |
| 渠道不可用 | 查询历史、接受有界请求、保留待恢复任务 | 新渠道执行按容量与风险限制 | 把超时视为明确拒绝 |
| 账务不可用 | 已验证的渠道事实查询、证据保存 | 依赖记账结果的履约与结算 | 删除支付成功事实或绕过资金约束 |
| 消息积压 | 扫描持久化状态、按优先级恢复 | 无界新增任务、盲目并行重放 | 将消息送达当成业务效果完成 |
| 对账资料缺失 | 已获取范围内的暂时核对 | 宣称全量对账完成 | 把未获取报告视为零交易 |
| 银行出款未知 | 原指令查询、保留占额、人工核查 | 同一权利再发新付款 | 租约到期即释放资金占用 |
| 展示投影滞后 | 展示带水位的历史查询 | 用缓存批准资金动作 | 修改源凭证迎合缓存 |

降级开关应绑定业务含义、作用域和审批权限。关闭自动重试不等于关闭资金核查；暂停新支付不等于丢弃已经发生的交易。

## 3. 背压、隔离与重试预算

- 分别设置受理入口、渠道执行、查询恢复、消息消费和结算批次的容量边界。
- 为不同商户、渠道和操作类型保留合理隔离，避免单一故障耗尽所有资源。
- 重试采用退避、抖动和渠道限流契约；恢复任务不能无限抢占正常请求。
- 重试预算不足时应停止自动执行并保留任务，不能改用新资金操作身份。
- 熔断仅影响后续调度决策，不证明在途操作失败。
- 队列长度之外，还应观察未知操作账龄、待记账金额、预留占用与差错敞口。

具体并发、超时和速率需通过实际容量测试确定；本仓库没有默认生产参数。

## 4. 幂等、权限与安全边界

### 身份与授权

- 商户认证后从受控身份上下文确定商户边界，不信任请求自行声明的身份。
- 支付、退款、收款账户变更、人工修账与大额出款分别授权。
- 敏感变更采用明确的审批、操作者身份和审计轨迹，审批不能替代资金约束。
- 平台控制账户与商户账户分开管理，不允许通过接口参数任意指定对手方。

### 外部输入与回调

- 按渠道契约验证来源、签名或认证、重放窗口及事件对象类型。
- 验签之后仍需核对商户、渠道账户、环境、币种、金额、原操作引用和状态合法性。
- 通知无法关联时隔离，不猜测“最近的一笔订单”。
- 对账单验证来源、范围、完整性、文件摘要与解析规则；hash 本身不是来源认证。

### 敏感数据

- 尽量由渠道托管或令牌化支付凭证；是否涉及额外合规义务取决于实际数据范围。
- 日志与指标使用业务关联标识，避免记录完整卡号、验证码、签名密钥和访问令牌。
- 密钥和凭证使用受控存储，按环境隔离并支持轮换、撤销及最小权限访问。
- 原始通知、银行报表与人工证据限定保存范围；公开仓库仅保留虚构样例。

## 5. 审计与证据链

审计至少回答：谁发起、执行了哪种操作、使用哪个规则版本、依据什么外部证据、修改了哪个业务投影，以及是否经过审批。

审计事件不替代业务唯一约束，也不替代原始凭证。业务记录、权限操作与证据引用应能相互关联；追踪 ID 不能充当资金幂等键。

已提交账务事实通过冲正或调整纠正。审计与财务数据的保留期限应依据适用法律、合同和审计政策制定，不把“永久保留所有个人数据”当作通用方案。

## 6. 分片与跨地域一致性

分片键不仅决定容量分布，也决定原子约束能否成立。

- 优先把共同校验的余额、额度与凭证放入同一事务域。
- 跨分片转移若采用预留与在途权利，必须处理确认、释放、迟到成功与双份可用余额。
- 跨分片不等于天然最终一致，Saga 也不提供事务隔离。
- 多地域强一致可以通过协调事务实现，但存在协调成本；并非所有支付都必须单地域写入。
- 异步复制后的“最后写入获胜”不能自行维护余额不透支等约束。

Google Cloud 对 Spanner 外部一致性的说明证明跨服务器、跨数据中心强一致是可实现的；这不是对所有数据库或多活方案的通用保证。[12]

## 7. 灾备恢复顺序

备份恢复成功只是存储恢复，不是业务恢复完成。开放资金写入前，应完成以下检查：

1. 明确恢复点、复制水位与可能遗漏的提交历史。
2. 隔离旧写入者，确认新权威能够安全接管本地操作。
3. 核对业务操作、资金事实、账务凭证、预留和去重记录是否完整。
4. 扫描恢复点附近已持久化、可能已经发送的渠道及银行操作。
5. 按原身份查询外部结果，补齐缺失证据；不能仅凭本地“未成功”重新执行。
6. 检查消息重放范围是否超过去重记录保留范围，必要时暂停相关消费者。
7. 在受限范围验证余额、额度和关键不变量，再逐步开放新操作。

数据库 fencing 可以限制旧本地写入，不能撤销已经发往渠道的扣款或出款。外部效果仍需幂等契约、查询与证据恢复。

## 8. 运行与演练目标

需要验证的能力包括：渠道超时后查单收敛、账本提交后丢响应、重复回调、退款确认与释放竞争、结算未知、旧任务迟到、跨地域切换及历史消息重放。

演练应记录注入位置、实际资金替代物的状态、恢复操作和最终不变量。模拟渠道测试不等同于真实银行环境验证；真实资金接入还需机构、合同、安全与合规审查。

指标阈值、告警等级和恢复目标应按业务体量、合同及风险承受能力确定，不能用未经验证的数字包装成 SLA。
