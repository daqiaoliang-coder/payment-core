# 支付生命周期与证据模型

> 状态：设计草案，未实现。日期：2026-10-30。
> 本文是通用商户即时收款的参考设计，不代表可运行系统，不承诺金融生产可用。

## 1. 范围与阅读约定

- **设计建议**：除明确标为“产品事实”的内容外，本文均是待实现、待验证的设计约束。
- **产品事实**：仅描述所引渠道产品的公开文档，不推导其他渠道具有相同契约。
- 设计输入来自本项目已确定的对象分离、证据驱动状态和不确定结果处理原则。
- 模块化单体只是后续实现建议，不能据此声称当前已有服务、数据库或消息队列。
- 主路径为商户发起即时收款，支付人完成支付，渠道返回证据，核心确认资金事实。
- 授权后捕获、退款、拒付是需要区分的生命周期分支，不展开账本分录和结算规则。
- 本文使用文字和状态表；图源由项目集中维护，不在此另建图文件。

## 2. 对象关系与职责

| 对象 | 表达什么 | 不能替代什么 |
| --- | --- | --- |
| 业务订单 | 商户销售、服务与履约约定 | 不能以订单完成证明渠道已收款 |
| 支付单 | 某次收款意图、固定应收金额与币种 | 不能混入渠道重试或账本凭证状态 |
| 渠道尝试 | 支付单下固定渠道账户、区域和路由的收款执行上下文 | 不是一次 HTTP 请求 |
| 资金操作 | 授权、扣款、捕获、退款、拒付等操作及证据 | 不是通用的“支付状态”字段 |
| 账本凭证 | 资金事实在账务规则下形成的记录 | 不是渠道是否扣款的证据来源 |

- 一个业务订单可关联多张支付单，但即时收款基线只允许一个未解除风险的收款意图。
- 一张支付单可保留多个历史渠道尝试；前一尝试可能扣款时，不允许自动开始下一尝试。
- 一个渠道尝试可关联授权与捕获等多个资金操作，每个操作有自己的身份与证据历史。
- 退款以独立资金操作引用原扣款或捕获，不通过创建另一笔收款来表达。
- 拒付案件与原资金操作关联；争议通知、实际扣回和后续返还分别保存。
- 一项资金操作可以产生多个证据版本；证据数量不等于应记账次数。
- 一项已确认资金事实可能尚无账本凭证；凭证数量及拆分由账务规则另行定义。
- 本文的渠道尝试状态表限定收款路径，不能直接套用为退款或拒付状态机。

## 3. ID 与唯一性作用域

| 标识 | 建议作用域与用途 | 约束 |
| --- | --- | --- |
| `merchant_order_id` | 商户内的业务订单引用 | 以商户身份组成唯一键，不能跨商户查单 |
| `payment_id` | 核心生成的支付单身份 | 不因网络重试变化；关联固定收款条款 |
| `attempt_id` | 核心生成的渠道尝试身份 | 固定渠道账户、环境、区域及请求关联信息 |
| `operation_id` | 核心生成的资金操作身份 | 授权、捕获、退款分别分配，不复用 |
| `merchant_idempotency_key` | 商户、接口操作类别及约定命名空间内 | 绑定规范化请求参数，不等同订单号 |
| `provider_idempotency_key` | 渠道产品定义的幂等空间 | 绑定资金操作和目标端点，不能假设全球有效 |
| `provider_reference` | 渠道、渠道账户、环境及产品对象类型内 | 保留区域等必要维度，不能仅按裸 ID 关联 |
| `event_id` | 来源渠道、账户、环境内的事件标识 | 去重投递，不足以去重同一资金事实 |
| `journal_id` | 账务域中的凭证身份 | 通过资金事实引用追溯，不与支付单 ID 混用 |
| `correlation_id` | 日志和跨边界追踪 | 非业务唯一键，不承担资金幂等 |

- 即使内部 ID 使用全局唯一生成方案，权限检查仍必须包含商户和环境边界。
- 同一幂等键换金额、币种、收款主体或原操作引用应返回冲突，不能悄悄新建对象。
- 返回给商户的超时结果应保留可查的支付单身份，避免商户以新订单号规避未知状态。
- 网络重试复用操作身份、渠道幂等键和有效载荷；新尝试意味着新的业务决策。
- 渠道保留期限、账户作用域和区域限制见[一致性与恢复](consistency-and-recovery.md)。

## 4. 金额与币种契约

- 所有金额以整数最小货币单位加 `currency` 表达，不用二进制浮点数传递或累加。
- 币种精度通过受控元数据解析；不得把所有币种统一乘以或除以 100。
- 例如两位精度币种的 100 表示 1 个主单位，零位精度币种的 100 表示 100 个主单位。
- 三位精度币种的 1000 表示 1 个主单位；示例不代替具体渠道的金额编码契约。
- 渠道适配层应核对币种精度差异，显式转换并保存转换依据，禁止静默截断。
- 收款及退款请求应校验正数、整数范围、渠道上下限、币种支持和累计金额溢出。
- 即时收款基线要求确认金额与支付单应收金额一致；部分收款不是默认支持能力。
- 部分捕获只能增加已确认捕获金额，不能把未足额的支付单标成全额支付成功。
- 金额或币种不匹配的证据进入差错，不自动改订单金额，不自动换汇后确认成功。

## 5. 证据优先于界面与传输结果

- 支付人跳转到成功页面、SDK 回调、HTTP 2xx 都不是通用资金成功证据。
- 受理只证明请求被接收；授权只证明额度被授权，不等于扣款或捕获完成。
- 可信证据须来自经认证的渠道接口、通过验签的通知或经过来源核验的对账材料。
- 来源可信与业务含义成立是两个条件：验签通过的“已受理”仍然不是资金成功。
- 渠道适配契约应列明证据类型、关联 ID、金额币种、最终性和可能的后续调整。
- 查询未找到记录不自动证明未执行；需要核对查询范围、可见性延迟和渠道保证。
- 成功的收款事实不等于不可撤销、不等于已结算，也不等于商户可提现。
- 保留原始证据摘要、来源、发生时间、接收时间、验证结论和采用的适配规则版本。

## 6. 渠道尝试状态定义

| 状态 | 本地含义 | 默认动作 |
| --- | --- | --- |
| `CREATED` | 尝试身份已持久化，尚未进入发送边界 | 可校验或在确认未发送时取消 |
| `SUBMITTED` | 发送意图已提交，发送已开始或可能开始 | 等待响应；不能据此认定已受理 |
| `PROCESSING` | 已有渠道证据说明收款流程仍在进行 | 等待通知或按渠道规则查询 |
| `UNKNOWN` | 本地无法确定渠道是否已产生资金效果 | 保持原身份核查，阻止新的扣款尝试 |
| `SUCCEEDED` | 可信资金操作证据确认本尝试收款成功 | 固化成功事实，推进后续门禁 |
| `FAILED` | 有证据确认本尝试失败且不会再扣款 | 保存失败依据，才可评估新尝试 |
| `CANCELLED` | 未发送已封闭，或渠道确认取消且不会再扣款 | 保存取消依据，解除对应执行权限 |

- `UNKNOWN` 是本地知识状态，不是渠道业务事实；渠道未必有同名状态。
- `SUBMITTED` 允许“本地记了发送意图，但进程尚未真正发出”的崩溃窗口。
- `PROCESSING` 可带“需支付人动作”“已授权待捕获”等子事实，不增加混淆的成功状态。
- 失败码、连接超时、截止时间到达或支付人关闭页面，都不能单独触发失败终态。

## 7. 状态转移表

| 原状态 | 条件或证据 | 目标状态 | 必须伴随的处理 |
| --- | --- | --- | --- |
| `CREATED` | 发送身份与操作参数已固定，执行权已取得 | `SUBMITTED` | 提交发送意图后才越过网络边界 |
| `CREATED` | 本地取消与发送领取互斥，确认从未发送 | `CANCELLED` | 封闭发送权限，防止旧任务继续执行 |
| `CREATED` | 本地校验拒绝且保证没有外部执行 | `FAILED` | 保存拒绝依据，不提交渠道请求 |
| `SUBMITTED` | 渠道确认仍处理中或仅授权 | `PROCESSING` | 保留渠道对象引用与下一步条件 |
| `SUBMITTED` / `PROCESSING` | 超时、失联或证据不能确定结果 | `UNKNOWN` | 创建或更新持久化核查任务 |
| `UNKNOWN` | 查询确认仍在处理，且无矛盾证据 | `PROCESSING` | 保持原尝试与操作身份 |
| `SUBMITTED` / `PROCESSING` / `UNKNOWN` | 可信收款成功证据，主体和金额币种匹配 | `SUCCEEDED` | 同时记录资金事实及后续事件 |
| `SUBMITTED` / `PROCESSING` / `UNKNOWN` | 确认失败且不能再发生扣款 | `FAILED` | 核实授权、捕获及在途请求均已封闭 |
| `SUBMITTED` / `PROCESSING` / `UNKNOWN` | 确认取消生效且不能再发生扣款 | `CANCELLED` | 取消请求被受理并不足够 |
| 任意状态 | 重复的同一业务事实 | 不变 | 留下投递审计，不重复产生业务效果 |
| 任一终态 | 迟到的相反证据或无法解释的资金事实 | 不直接覆盖 | 保存证据、冻结相关门禁、进入差错处理 |

- 未列出的转移默认禁止；状态更新应校验版本和证据，不能按通知到达顺序覆盖。
- 旧的处理中通知不得把 `SUCCEEDED` 回退；再次查询也不能抹去已有成功证据。
- 终态矛盾不通过丢弃事件解决；核实后追加纠正记录，明确谁依据什么调整了投影。
- 若失败后证实实际扣款，必须纳入资金事实并处理重复收款风险，不能继续对外声称未收款。
- 退款或拒付是后续独立事实，不是本表中成功到失败的合法转移。

## 8. 支付单与订单如何得出结果

1. 商户以业务订单引用、金额、币种及幂等键请求收款，核心校验商户与参数绑定。
2. 支付单及首次尝试身份持久化后，再按既定渠道路由提交对应资金操作。
3. 核心只依据可信资金证据更新尝试和支付单，不以支付人浏览器回跳驱动履约。
4. 足额、同币种、正确商户的收款事实构成支付成功依据；异常多收款进入差错。
5. 支付单支付事实、记账状态和履约资格分别输出，不压缩成一个 `success` 布尔值。
6. 商户接收支付结果后仍应按事件身份和业务事实去重，履约只执行一次业务效果。
7. 订单主动关闭时若收款尚未知，订单可标记停止履约，但支付核查不能停止。
8. 关闭订单的迟到收款应形成待处置事实，由商户策略选择履约或退款，不能忽略。

- 尝试失败不必然等于支付单最终失败；只有无成功、无在途、无未知风险才可关闭收款。
- 商户界面应明确区分“处理中”“待核实”“支付成功待记账”，避免引导重复支付。
- 对账发现第二笔真实扣款时，两笔资金事实都应保留，不能用支付单唯一成功投影吞掉第二笔。

## 9. 授权、捕获与撤销

- 即时收款可由渠道在同一产品流程内完成扣款，也可能暴露授权与捕获两个阶段。
- 授权成功仅记录授权额度、币种、有效期和渠道引用；收款尝试仍不因此成功。
- 捕获以独立 `operation_id` 和幂等键执行，引用原授权，并校验剩余可捕获额度。
- 仅当可信捕获或扣款证据成立，才确认相应收款金额；捕获请求受理不等于完成。
- 多次捕获、增量授权和超额捕获不是基线能力，接入前须补充渠道规则与并发约束。
- 撤销未捕获授权与已扣款后的退款不是同一种操作，不能复用含糊的“取消支付”。
- 捕获与取消竞争时保持资金事实优先；不能因取消界面成功就忽略在途捕获。
- **产品事实**：Stripe PaymentIntent 具有自己的状态流程，不能逐名等同本文状态。
- Stripe 的 `requires_capture` 与 `succeeded` 含义不同，适配时应结合捕获模式解释。
- 来源：[Stripe PaymentIntents](https://docs.stripe.com/payments/payment-intents)。

## 10. 退款与拒付

- 退款必须引用原成功收款操作，并携带独立退款身份、商户幂等键、金额及币种。
- 退款额度原子预留；在途及 `UNKNOWN` 退款继续占用额度，不能因超时自动释放。
- 退款资金事实与退款记账状态分别维护；退款请求受理不可立即当作资金已退回。
- 退款结果未知时复用原操作核查，不以新退款键“补发”；并发额度规则见恢复文档。
- 确认退款完成只改变退款累计事实及相关权益，不把原支付成功改写为失败。
- 后续退款退回、撤销或失败证据应追加资金调整与差错，不销毁原退款证据。
- **产品事实**：Adyen 的 `REFUND` 通知中 `success=true` 表示校验通过，之后仍可能退款失败。
- 因此该字段不能直接映射成所有渠道通用的“退款最终成功”，需保留后续事件处理路径。
- 来源：[Adyen Refund](https://docs.adyen.com/online-payments/refund)。
- 拒付案件的开启不自动等同实际扣回；资金扣回与申诉返还需要各自的可信证据。
- 拒付与退款并发可能导致重复返款风险，应冻结有争议额度并核查，而非简单相减。
- 即使全额退款或最终拒付，历史支付成功事实仍成立；净资金结果通过独立操作体现。

## 11. Webhook：从原始字节到业务事实

1. 保留原始请求 body 字节及必要签名头；对要求原始字节验签的渠道，不得先重排或转换正文。
2. 根据受控的端点、账户和环境配置选密钥；不能信任 body 自报的商户来选择信任域。
3. 按渠道规范选择原始正文或指定字段的签名构造方式；算法、时间戳和重放校验也遵循该契约。
4. 验签失败不得更新支付事实；记录脱敏的失败原因，响应方式遵循渠道契约。
5. 验签成功后核对事件类型、对象类型、商户归属、渠道账户及生产/测试环境。
6. 将渠道引用映射到本地操作和尝试，核对操作类别、原支付引用、金额及币种。
7. 通知不含足够金额或引用信息时，先持久化待核查状态，再以认证查询补足证据。
8. 无法关联或字段不符的通知进入隔离与差错，不猜测最近订单，不直接确认成功。
9. 对已验证且已可靠保存的通知按渠道规范及时应答，把业务处理交给可恢复任务。
10. 本地持久化失败不得假装已可靠接收；传输应答与业务成功是两种不同结果。

- **产品事实**：Stripe 验签需要原始 body；其 Webhook 可能重复投递，且不保证事件顺序。
- 来源：[Stripe Webhooks](https://docs.stripe.com/webhooks)。
- **设计建议**：以“来源作用域 + 事件 ID”去重投递，以“资金操作 + 事实类型 + 渠道事实身份”去重业务。
- 不同事件 ID、查询响应和补单材料可能证明同一事实，不能因此重复确认金额或重复记账。
- 多次部分捕获、退款和拒付调整是真实不同事实，不能仅以支付单 ID 粗暴去重。
- 乱序事件依据渠道版本、操作关联及状态约束处理；只有时间戳而无顺序保证时应查询核实。
- 相同事件 ID 却出现不同载荷应保存摘要冲突并告警，不能将其当作普通重投静默忽略。
- 原始通知可能含敏感数据，应受限访问并制定保留策略；业务审计保留最小必要证据。

## 12. 交接边界

- 支付核心负责解释渠道证据、保持操作身份及输出可追溯事实；不能把该职责推给商户页面。
- 账务负责事实对应的凭证与记账结果，结算负责后续可结算与出款条件，本文不重复其规则。
- 事务、消息投递、外部副作用及恢复门禁详见[一致性与恢复](consistency-and-recovery.md)。
- 状态图与超时恢复时序见[图集](diagrams/README.md)，图中的终态不允许丢弃相反的迟到资金证据。
