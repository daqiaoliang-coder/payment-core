# 账本、余额与资金约束

> **参考设计 / 未实现、未验证**
> 本文是 payment-core 架构设计，不是可运行服务、会计政策或生产资金安全承诺。
> 以下不变量均为拟议的设计约束，不能误称为数据库、TigerBeetle 或其他厂商的自动保证。

## 1. 边界与确认前提

交易域回答“支付、退款发生了什么”，账务域回答“谁对谁形成了何种权利义务”，资金域回答“钱实际在哪里”。
三者通过业务标识、原始证据和凭证关联，不以某一域的状态直接替代另外两域的事实。

| 边界 | 记录对象 | 不可推导的结论 |
| --- | --- | --- |
| 交易 | 授权、扣款、退款、拒付及渠道结果 | 扣款成功不证明平台银行已经到账 |
| 账务 | 应收、应付、收入及其借贷变化 | 借贷平衡不证明金额、主体或确认时点正确 |
| 资金 | 银行入出账、渠道待结算资金、受限资金 | 银行有钱不代表某商户具有出款权利 |
| 合同与政策 | 主体角色、收费条件、确认依据、结算权利 | 技术状态不能自行决定收入确认 |

平台是否承担应付商户、是否享有应收渠道权利，应由合同、法律主体与会计政策明确。
纯网关仅传递支付指令时，不能套用平台自有资金或应收应付确认；可采用业务备查记录，并另行确认合同服务费。
客户资金、平台自有资金及不同法人账套必须区分；技术分户账不自动等于法律上的资金隔离。

## 2. 概念实体数据字典

下表是概念模型，不指定数据库、字段类型宽度或可直接部署的表结构。
已提交的 journal 与 entry 只追加；审批草稿、可变操作状态与源账本分离。

| 实体 | 核心字段 | 语义与约束 |
| --- | --- | --- |
| LedgerBook（账套） | book_id、legal_entity_id、policy_version | 明确法律主体、政策与封账边界；不能跨账套直接借贷抵销 |
| CurrencyMetadata（币种元数据） | currency、minor_unit_exponent、version、effective_at | 金额单位解释依据；固定版本，历史金额不能随配置被重新解释 |
| Account（账户） | account_id、book_id、owner_scope、merchant_id、currency、category、normal_side | 账户固定币种与归属；商户子账户和平台控制账户分别授权 |
| Journal（凭证） | journal_id、book_id、operation_id、kind、effective_at、recorded_at、policy_version | 一次原子记账的头部；提交后不可修改、删除或换业务归属 |
| Entry（分录） | entry_id、journal_id、account_id、side、amount_minor、currency | 金额为正整数，以借贷方向表达变化；币种必须匹配账户 |
| BusinessOperation（业务操作） | operation_id、merchant_id、business_id、operation_type、payload_digest | 标识一次经济动作；请求重试、事件重投共用同一操作身份 |
| ReservationEvent（预留事件） | reservation_id、operation_id、account_id、amount_minor、event_type、evidence_id | 追加预留、确认或释放事实；当前预留由事件归并，避免覆盖轨迹 |
| CorrectionLink（修正关联） | correction_journal_id、original_journal_id、reason、approved_by | 补偿、冲正必须引用原始凭证；保存审批和修正范围 |
| Evidence（证据索引） | evidence_id、source_type、source_ref、digest、observed_at | 关联渠道回执、报表、合同版本；不在公开设计中放真实账户信息 |
| BalanceProjection（余额投影） | account_id、posted_balance、active_reserved、sequence、as_of | 可重建读模型；必须说明消费水位，不能伪装成实时源账本 |
| PostingCheckpoint（控制状态） | account_id、version、posted_total、reserved_total | 与源记录原子维护的资金校验状态；不等于异步展示缓存 |
| OutboxRecord（待投递事件） | event_id、journal_id、operation_id、payload_version | 与凭证同一提交边界产生；投递重复由消费者去重 |

业务引用还应携带原支付、退款或出款标识；仅有 HTTP 请求 ID 不足以识别经济动作。
证据可存于受控存储，账本保留稳定引用与摘要；摘要不能替代来源可信度和访问控制。

## 3. 金额、时间与余额口径

- 金额持久化为最小单位整数并绑定币种元数据；禁止用 float 累加、比较或计算费用。
- 不默认所有币种有两位小数；展示金额转换由指定版本的币种元数据决定。
- 费率按精确十进制或有理数表达，明确舍入方向、舍入层级与尾差归属科目。
- 金额上界、聚合溢出和负值输入需要校验；不能通过整数溢出绕过余额检查。
- 汇兑必须建模两侧币种、汇率来源、报价时点和差额；不能把异币种数字直接相加配平。
- effective_at 表示经济生效时间，recorded_at 表示记录时间；营业日另按版本化日历派生。
- 迟到事件保留原事件时间，但不得绕过已关闭会计期间；按批准的调整政策进入开放期间。

| 名称 | 口径 | 典型误用 |
| --- | --- | --- |
| 已入账余额 | 按账户正常方向汇总已提交分录 | 把应付余额当成银行存款 |
| 预留 | 尚未完成动作对权利或额度的占用 | 因请求超时就视为零 |
| 可用余额 | 指定用途下，已入账权利扣除有效占用及限制 | 把所有用途共用一个余额字段 |
| 可结算余额 | 已满足合同期限、争议与风控条件的权利 | 把新扣款立即列为可出款 |
| 可执行出款额 | 可结算权利、未占用额度及可用资金的共同约束 | 仅看商户应付就执行银行付款 |

资产类借方增加、负债及收入类贷方增加；报表须说明符号，不能将所有账户统一解释为“贷减借”。
商户应付的示例口径：可用 = 已确认应付余额 − 有效出款预留 − 其他互斥受限部分；各扣减集合不能重叠。
可结算还须筛选到期明细和合同规则，不能单靠汇总余额反推；资金准备不足时即使有权利也不能执行出款。
退款额度预留与商户出款预留是不同约束；若同时影响商户应付，必须关联同一占用来源，防止漏扣或双扣。

## 4. 十个可验证不变量

以下约束需通过实现审查、并发测试、故障注入及离线核查验证；本项目尚未执行这些验证。
“不变量成立”仅说明满足指定约束，不替代交易真实性、合同合法性和收入确认审查。

| 编号 | 设计约束 | 验证办法 | 违反示例 |
| --- | --- | --- | --- |
| L1 | 每份凭证在每个账套、每种币种内借方合计等于贷方合计，分录整体可见 | 分币种重算并注入提交中断 | 借 CNY 100、贷 USD 100，被数值相等误判为平衡 |
| L2 | 已提交 journal/entry 不覆盖、不删除；补偿与冲正均可追溯原凭证 | 审计写入权限、比对历史快照和修正引用 | 直接把原手续费从 1 元改为 2 元 |
| L3 | 一次业务记账动作只有一份有效原始凭证，重试不重复产生资金影响 | 按业务操作唯一键聚合并发重放 | 回调和主动查询各记一次收入 |
| L4 | 分录账户归属经过授权，币种与操作一致，商户隔离不可由请求参数绕过 | 交换 merchant_id、account_id、currency 做拒绝测试 | 商户甲退款扣了商户乙的应付账户 |
| L5 | 金额可精确解释，无 float、隐式币种换算及越界聚合 | 检查边界值、非两位币种和舍入用例 | 将无小数币种的 100 单位错误解释为 1 单位 |
| L6 | 对禁止透支的用途，余额检查与 reserve/post 的资金变化在同一原子边界 | 两笔竞争剩余额度的操作同时提交 | 余额 100，两请求各查到 100 后各扣 80 |
| L7 | 每份预留只终结一次；确认与释放互斥，UNKNOWN 无确定证据不释放 | 并发确认/释放、重复终态和超时故障注入 | 已付款后超时任务又释放预留 |
| L8 | 退款成功累计 + 处理中预留不超过适用的普通原路可退上限 | 并发多次部分退款并加入拒付占额案例 | 原付 100、成功退 70、预留 20，又受理退款 20 |
| L9 | 指定水位的投影等于源账本重放结果；资金批准不依赖落后缓存 | 重建投影、注入事件乱序和重复 | 展示缓存未扣上一笔出款，又批准下一笔 |
| L10 | 跨分片未完成的资金移动不能形成可重复支用的余额 | 在每个提交点中断并恢复跨分片流程 | 源扣款未成功，目标已开放可用余额 |

L3 的唯一键应覆盖账套、商户、操作类型和稳定业务动作标识；一笔支付的入账、退款、到账是不同动作。
政策版本属于动作内容与审计上下文，不能仅换规则版本就绕开唯一键，重记同一经济动作。
L4 允许经授权使用平台控制账户作为商户分录的对手方，但不允许任意商户之间相互抵扣。
L7 是本文采用的单次终结模型；更复杂的分次捕获需要独立动作与总额度约束，不能悄悄复用已终结预留。
L8 的上限以已确认的原支付可退基数为起点，扣减适用拒付、已撤销部分及其他排除项，不能重复扣减同一事实。
该上限不再扣一次已成功退款，因为成功退款已位于不等式左侧；渠道规则与合同应决定各类调整的适用性。
迟到拒付若使历史占用超过新上限，应立即阻止新增退款、记录超额差错并人工处置，不能删历史退款或伪释放预留。

## 5. 100 元收款、1 元手续费的示例

前提：同一平台账套、CNY 元数据为两位小数；平台承担应付商户义务并享有应收渠道权利。
合同约定从 100 元收款中扣除平台手续费 1 元，且该时点收入确认条件已满足。
示例忽略税、渠道费、准备金、争议和汇兑；这里只演示一种业务合同，不是普遍会计规则。
表中展示单位为元，持久化整数分别为 10000、9900、100；dr 表示借，cr 表示贷。

| 凭证 | 触发及所需事实 | 借方 dr | 贷方 cr |
| --- | --- | --- | --- |
| J1 收款确认 | 扣款及合同确认依据充分，非仅授权成功 | 应收渠道 100 | 应付商户 99；手续费收入 1 |
| J2 渠道到账 | 银行入账与渠道款项完成匹配 | 银行存款 100 | 应收渠道 100 |
| J3 商户出款 | 有充分资金扣账及义务履行证据 | 应付商户 99 | 银行存款 99 |

| 时点 | 应收渠道余额 | 银行存款余额 | 应付商户余额 | 已确认手续费收入 |
| --- | --- | --- | --- | --- |
| J1 后 | 借 100 | 0 | 贷 99 | 贷 1 |
| J2 后 | 0 | 借 100 | 贷 99 | 贷 1 |
| J3 后 | 0 | 借 1 | 0 | 贷 1 |

J1 平衡不能证明应该向该商户支付 99 元；仍须校验商户归属、收费合同和交易证据。
若收入条件未满足，应按批准政策确认相应负债或递延项目，不得为了凑齐示例直接确认收入。
真实出款可能先银行扣账、后收款行入账，应引入出款在途等科目；J3 是省略中间阶段的已完成情形。
手续费退款、拒付、渠道费补扣须分别判断责任和合同依据，不能机械复制 J1 的全额反向分录。
纯网关没有上述应收应付或资金控制事实时，不能照搬 J1—J3，更不能把代传指令记为自有银行资产。

## 6. 防并发超扣与幂等提交

下表描述事务意图，不提供伪装成可执行服务的 SQL；具体实现须证明存储引擎的隔离与恢复语义。

| 步骤 | 同一资金原子边界内必须完成的事 | 失败语义 |
| --- | --- | --- |
| 识别动作 | 根据稳定业务键占位，比较商户、金额、币种和内容摘要 | 同键同内容返回既有结果；同键异内容拒绝 |
| 锁定额度 | 对相关控制状态加行锁，或采用带版本和余额条件的原子更新 | 冲突重读重算；不得沿用旧的余额判断 |
| 检查规则 | 校验账户归属、币种、可用/可退额度、账户限制与规则版本 | 任一条件不满足不产生部分资金变化 |
| 原子记录 | 追加完整凭证或预留事件，同时更新控制状态与业务动作结果 | 提交失败整体回滚，不能留下半张凭证 |
| 发布依据 | 与源记录一并写入待投递事件，再由异步机制投递 | 投递失败重试，不重新记账 |

仅在一个数据库事务里先读后写，不代表自动防超扣；必须具备足够隔离、受锁保护的校验或原子条件更新。
多账户操作采用稳定锁顺序并处理死锁；遇到序列化失败应重新读取规则与额度，再复用原业务身份重试。
Redis 锁可以降低冲突或调度任务，但租约过期、网络分区和进程暂停不得使其成为资金正确性的唯一机制。
调用渠道或银行不处于本地事务内；应先持久化操作意图与预留，再发送稳定外部标识，最后凭证据收敛。
本地提交成功但响应丢失时，调用方按原键查询或重试，不能生成新业务动作规避“不知道是否成功”。
幂等记录的生命周期须覆盖可能的回调、账单迟到和审计窗口，不能短期过期后把旧动作当新动作接受。

## 7. 退款预留与未知结果

普通原路退款受原支付的可退权利约束；授信、赔付或线下补偿属于不同业务，不能借此绕过退款上限。

| 事件 | 额度处理 | 所需依据 |
| --- | --- | --- |
| 受理退款 | 原子增加处理中预留，同时校验 L8 | 原支付、币种、商户、适用上限和业务唯一键 |
| 明确退款成功 | 原子减少对应预留并增加成功累计，追加退款凭证 | 可验证的渠道成功证据和既有退款标识 |
| 明确失败或取消 | 原子终结并释放对应预留 | 足以确认未退款且不会继续执行的渠道终态 |
| 超时、查询不明、回调缺失 | 保持 UNKNOWN 与占额，进入查询及差错流程 | 超时本身不是失败证据 |
| 重复或矛盾终态 | 重复证据去重；矛盾证据隔离升级 | 原始响应、查询时间、报表和事件链 |

退款金额、手续费返还和拒付占额分别记录；同一拒付与退款是否重叠须按渠道证据判断，不能简单重复扣减。
外部退款确认与本地入账之间若发生故障，重放原动作完成入账，而不是再次调用渠道创建退款。
TigerBeetle 的两阶段转账中，一笔 pending 仅可被 post 或 void 终结一次，不能泛化为同一 pending 可反复部分 capture。
即使某底层机制支持预留自动过期，也不能把它当作外部 UNKNOWN 退款或出款已经失败的证据；二者生命周期须解耦。

## 8. 源账本、投影与跨分片边界

源账本与预留事件是恢复依据；展示、统计和搜索投影可以异步，但必须暴露更新时间及消费水位。
投影重建按稳定序列重放、按事件标识去重；新投影在同一水位比对通过后才切换读流量。
资金校验使用与源记录原子维护的控制状态，或在同一隔离边界内读取源事实；不用异步报表余额批准付款。
发现投影差异应隔离受影响的资金操作、重建核验；不能反向修改源凭证以迎合缓存。
分片键优先保证同一资金约束在一个原子边界内；“同一商户”并不必然涵盖平台银行或渠道控制账户。
跨分片转移可设计为源侧预留、在途权利、目标侧有证据确认，每侧凭证都在自身账套和币种内平衡。
目标可用的开放必须依赖源侧不可重复支出的承诺；中间超时保持在途与占额，由恢复流程继续收敛。
Saga 只能协调阶段与补偿，不能提供天然的全局原子性；需证明幂等、恢复、围栏与净额守恒。
若无法证明边界内的正确性，应限制跨分片资金操作或收敛到支持该原子约束的账务边界，不用“最终一致”掩盖风险。

## 9. 挂账、修账与验证计划

| 类别 | 典型情形 | 处置要求 |
| --- | --- | --- |
| 未决资金 | 权利义务明确，但渠道待结算或出款在途 | 使用明确在途/应收科目及外部标识，维护账龄，不误报为差错 |
| 差错待查 | 银行已到账但无法识别商户，或账单金额与入账不一致 | 在事实和政策支持下记待查科目，建差错单、owner、证据与期限 |
| 无资金确认依据 | 仅客户端超时，尚无资金变化证据 | 保留操作与预留，不为“有记录”而虚构银行分录 |

待查科目不是强行调平的垃圾桶；核对平衡但主体不明时仍不能释放可用余额或关闭差错。
修账先定位原凭证和证据，再追加有审批的冲正及正确凭证；部分补偿明确金额与范围，防止累计冲正超过原影响。
原凭证、修正凭证和关联关系按适用法律、合同及审计政策完整留存；到期归档或销毁须受控，不得以此篡改有效期间的资金历史。
封账后的调整记录审批、所属期间及对报表的影响，个人敏感数据的保留范围另行约束。
待实施验证包括：十个不变量用例、并发扣款/退款竞争、提交后丢响应、乱序回调、跨分片中断与投影全量重建。
验收证据应包含输入、故障点、持久化结果、金额核对和失败断言；本仓库没有这些测试执行结果。
