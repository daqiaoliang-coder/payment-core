# 清分、结算、出款与对账

> **参考设计 / 阶段 3 骨架已实现，未验证真实资金**
> 本文定义职责、资金边界与核查方法；阶段 3 骨架以模拟银行和模拟报告覆盖 S01—S10，不代表任何渠道或银行的生产承诺。
> 实际合同、报告字段、会计政策与渠道能力仍需另行确认。

## 1. 四个不同的业务事实

交易成功、账务确认和资金移动互有关联，但不共用一个足以表达全部事实的“结算成功”状态。

| 概念 | 回答的问题 | 核心产物 | 不能等同于 |
| --- | --- | --- | --- |
| 清分 | 一组交易应归谁、收多少费、哪天具备结算资格 | 版本化分配明细、应付及调整依据 | 银行已发生资金划拨 |
| 渠道结算 | 渠道按什么批次计算并清偿对平台或商户的款项 | 渠道结算批次、净额及转账参考 | 平台已向商户出款 |
| 商户出款 | 按合同把商户可结算权利转成付款指令并履行 | 出款单、资金预留、外部指令标识 | 指令受理即收款账户到账 |
| 银行到账 | 哪一方银行账户出现实际入账，价值日是什么 | 银行流水、入账金额与参考号 | 自动证明所有业务归属和费用均正确 |

银行到账需要注明方向：渠道到平台、平台出款扣账、商户收款入账是不同证据，不能只叫“到账”。
Adyen 的生命周期说明中，Settled 不代表已向商户支付；该语义用于提醒边界，不映射成所有渠道的统一终态。
纯网关不控制结算资金时，只记录可取得的渠道和商户结算证据，不能虚构平台收款或应付清偿链路。

## 2. 清分规则及可追溯输入

清分只按已定义的业务范围计算，不由临时页面展示或当前费率配置倒推历史结果。

| 规则维度 | 需要固化的内容 | 变更处理 |
| --- | --- | --- |
| 适用主体 | 法人、商户、业务类型、合同标识、渠道 | 防止用其他商户规则或跨主体净额抵销 |
| 费用 | 费率、固定费、计费基数、退款返费与拒付责任 | 新版本带生效边界；不覆盖旧明细 |
| 币种与舍入 | 原币、结算币、币种元数据、舍入层级、尾差归属 | 跨币种必须有明确汇率与换汇记录 |
| 资格 | 已确认条件、结算周期、准备金、争议冻结、最低付款约定 | 不把付款门槛误记为收入或免除应付 |
| 日历 | 时区、截点、营业日、节假日表及其版本 | 迟到数据按补充批或调整批处理 |
| 分配 | 收款、退款、费用、准备金释放与调整的归属规则 | 每项关联原交易、凭证及规则版本 |

每条清分明细保存输入事实版本、规则版本、计算结果、金额单位和证据引用；重算能解释为什么发生变化。
合同规则变更必须明确按交易时间、处理时间还是结算周期生效，禁止实现自行选择对结果有利的时间字段。
未满足收入确认条件的费用，按合同与会计政策处理；清分算出“费”不自动构成收入确认。
金额使用最小单位整数及币种元数据，不使用 float，不默认全部币种两位小数。
退款、拒付与准备金是独立调整类别；抵扣是否允许、作用在哪个周期，以实际权利义务为准。

## 3. 批次身份、冻结与重试

| 概念对象 | 身份与关联 | 关键约束 |
| --- | --- | --- |
| 内部清分批次 | batch_id、法人、商户范围、币种、周期、cutoff、输入快照 | 冻结后成员与规则不可暗改；与渠道批次不是同一标识 |
| 批次明细 | batch_item_id、business_operation_id、分配类型、amount_minor | 同一应结项目不得被两个有效批次重复消费 |
| 渠道结算批次 | provider、渠道商户范围、external_batch_id、结算币种 | 外部编号按渠道定义的范围解释，不能假定全局唯一 |
| 批次尝试 | attempt_id、batch_id、触发原因、开始/结束时间 | 重试只是执行尝试，不重新创造应付或记账动作 |
| 出款单 | payout_id、merchant_id、currency、收款配置版本、allocation_refs | 绑定冻结分配；多批合付或一批多付都要显式映射 |
| 外部付款意图 | payout_id、external_idempotency_key、渠道请求引用 | 重试使用原意图身份，不因超时换新单 |
| 批次调整 | adjustment_id、original_batch_id、original_item_id、reason | 迟到、退回及纠错追加记录，不覆盖原批 |

批次身份使用持久化业务标识，不能只靠运行时间命名；同周期再执行不意味着另一个经济批次。
规则升级不能通过生成新 batch_id 重新消费已结算项目；成员唯一性与动作幂等须分别约束。
批次冻结记录成员清单摘要、条数、分币种合计与规则快照；恢复任务先比对冻结内容，再继续未完成步骤。
建议分别维护计算、审批、资金、指令、核对等维度，避免单一 SUCCESS 同时表示算完、付出与核对通过。
批次部分完成后只处理未完成项；已付款项保持其原出款身份，不能整批重发掩盖中间失败。

## 4. 从权利到现金：资金准备与流动性

商户应付是账面义务，可结算是合同资格，可用是未被占用的权利，银行可动用资金是执行能力。
即使四者金额恰好相同，也要独立核验，不能以其中一个数替代全部检查。

| 执行前检查 | 证据与控制 | 不足时的处理 |
| --- | --- | --- |
| 应付与资格 | 清分明细、合同期限、争议与准备金条件 | 保留应付，说明不可结算原因 |
| 权利未重复占用 | 商户出款及退款等相关占用的统一关联 | 原子预留，拒绝重复消费同一份权利 |
| 资金可动用 | 银行确认余额、在途扣账、受限金额及有效付款预留 | 排队或按已批准规则缩减付款，不虚构到账 |
| 币种与主体匹配 | 付款主体、资金属性、收款配置及币种 | 不暗中跨商户、跨法人或跨币种挪用 |
| 操作窗口 | 银行截点、营业日、渠道限额、费用及资金安全缓冲政策 | 重排计划，保留原业务身份和原因 |

渠道应收和预计结算不能直接视为已到账现金；若合同允许预付，须独立建模资金来源、授信和风险承担。
流动性预测区分已确认资金、可靠度不同的预计流入和承诺流出；预估不能授权突破实际资金约束。
检查余额、建立预留与更新资金控制状态必须原子完成；Redis 锁不作为资金正确性的唯一保障。
银行与本地账本没有天然共同事务；发送前持久化付款意图，发送后用查询、回执、报表及银行证据收敛。
公开设计只使用逻辑账户角色，不新增真实银行账号、商户账号、凭证或鉴权信息。

## 5. 出款未知、失败与退回

| 观察事实 | 内部处置 | 是否可释放或另发 |
| --- | --- | --- |
| 尚未发送且明确取消 | 追加取消事实，原子终结原预留 | 可按确认范围释放；不产生外部付款 |
| 渠道仅受理 | 记录外部参考，持续占用权利与资金 | 不释放，不宣称商户到账 |
| 发送超时或结果不明 | 标为 UNKNOWN，按原外部标识查询并核对银行 | 不因到期释放，不用新出款单重发 |
| 确证最终拒绝且不会继续付款 | 保存最终证据，终结动作并释放对应预留 | 后续付款须显式关联替代关系和审批 |
| 银行已扣账、收款未证实 | 记录出款在途，保留义务履行状态的独立判断 | 不重复付款；按银行时效追踪 |
| 已有充分完成证据 | 原子完成既有动作及相应入账 | 重复通知去重，不再次扣减或释放 |
| 成功后资金退回 | 创建关联原出款的退回事件及修正凭证 | 不把旧成功改成失败；重新评估应付与资格 |

客户端错误、查询“未找到”和任务超时通常不足以证明未付款，应结合查询一致性窗口和渠道最终性约定。
查询与回调矛盾时，保留全部证据并升级差错；不能只取最后到达的一条覆盖历史事实。
渠道若不支持可靠幂等或查询，自动重试范围必须收紧，进入人工核查，而不是换单号碰运气。
重新付款必须已消除原指令继续执行的可能，并确认原预留、资金归还和应付处理，不允许双份在途。
退款同样要求“成功累计 + 处理中预留 ≤ 适用普通原路可退上限”，拒付等还应扣减适用额度。
UNKNOWN 退款不能仅因结算截点或预留时限到期释放；超额风险及迟到证据按[账本约束](ledger.md)处理。

## 6. 四层核对：逐笔与汇总并行

四层分别输出结果和证据；任一层匹配不能代替其他层，银行金额恰好一致也可能掩盖错商户或漏退。

| 层级 | 核对两侧 | 逐笔核对内容 | 汇总核对内容与差错例子 |
| --- | --- | --- | --- |
| 交易层 | 内部支付/退款事实 ↔ 渠道交易记录 | 原交易、退款关联、商户、金额、币种、状态与事件时间 | 按交易类型分组条数及金额；内部漏了成功退款 |
| 入账层 | 经证实应入账的业务动作 ↔ journal/entry | 动作唯一凭证、科目、归属、规则、确认时点 | 分币种借贷及应入账覆盖率；平衡但重复确认手续费 |
| 结算批次层 | 内部应结明细 ↔ 渠道批次报告 | 收款、退款、费用、拒付、准备金和调整的归属 | 毛额到净额桥接；退款落在不同周期导致差额 |
| 银行层 | 渠道汇款/出款记录 ↔ 银行流水及可得到账证明 | 参考号、方向、币种、金额、扣入账日与价值日 | 分账户分币种流入流出；渠道称已付但银行未见入账 |

逐笔匹配优先使用稳定渠道引用及业务关联，不仅靠“金额相同、日期相近”；启发式候选需要明确置信与审批。
交易层应区分授权、捕获、退款和拒付事件，不能拿授权总额对比已结算金额。
一对多、多对一匹配必须保存分配关系、分配金额及剩余未匹配量，防止同一银行流水被反复使用。
汇总按法人、商户范围、币种、渠道账户、营业日和事件类型分组，记录采用的口径与数据水位。
逐笔全匹配但汇总不符可能是重复导入；汇总相符但逐笔不符可能是正负差错抵销，两者都不能关闭差错。
可配置容差仅用于有依据的舍入或时间归属规则；容差必须批准、版本化并解释，不能用其吞掉本金差异。

## 7. 100 − 20 − 2 = 78 的限定示例

假设同一币种、同一渠道结算批次、相同统计范围：收款 100 元，退款 20 元，渠道费 2 元。
假设没有税、拒付、准备金、补扣、汇兑、跨期或其他调整，且费用确实由该批次扣除。
此例独立于账本文档的“平台手续费 1 元”案例；渠道费与平台收入不是同一科目。

| 组成 | 示例金额（元） | 核对证据 |
| --- | --- | --- |
| 纳入批次的收款 | +100 | 交易明细及渠道批次成员 |
| 纳入批次的退款 | −20 | 原支付关联、退款成功及批次归属 |
| 本批次扣除的渠道费 | −2 | 报表费用行、费率合同及费用承担方 |
| 预期净额 | 78 | 以上明细完整、无其他调整时才成立 |
| 银行实际入账 | 待银行证据确认 | 不能由预期净额直接生成“已到账”事实 |

若退款落在下一批，本批在无其他调整时可能为 98，后批再体现 −20；不能坚持让两个批次都匹配 78。
若结算币种不同，必须展示换汇金额、汇率和费用桥接；不能把原币 100、结算币 20、费用 2 直接相减。
净额为负时，应按合同结转、扣回或形成相应应收，不把负金额转换成向商户的普通正向付款。
演示数值不是行业费率、标准结算周期、固定准备金比例或可直接上线的会计政策。

## 8. 报表获取、完整性与去重

核对开始前先建立来源清单；“没有下载到记录”与“业务数量为零”必须严格区分。

| 检查点 | 需要保存或验证的内容 | 缺失时的结果 |
| --- | --- | --- |
| 范围声明 | 渠道、商户范围、币种、起止区间、报告类型、生成时点 | 标为范围不明，不能宣称全量核对完成 |
| 分页完整性 | 游标链、页数、总条数、最后一页标识、稳定快照或水位 | 缺页阻断完整性结论；重拉要去重并检测期间变化 |
| 文件完整性 | 预期文件清单、序号、文件大小、解析条数、声明合计 | 截断、缺文件或解析失败进入采集差错 |
| 时间口径 | 源时区、夏令时、半开区间、营业日及截点版本 | 保留原始时间，不按服务器日期随意分组 |
| 原件身份 | 提供方文件标识、版本、下载时间、原始字节摘要 hash | 同名异内容不能覆盖；新版本建立替代关系 |
| 重复导入 | 原件摘要及来源范围、明细业务标识、导入批标识 | 同文件重投不重复入账；不能只靠文件名判断 |
| 规范化质量 | 字段映射版本、字符编码、金额符号、币种、行摘要 | 不能把缺失金额默认成零，失败行必须隔离 |

摘要 hash 用于内容身份和变更检测，不证明渠道真实性；来源认证、传输与存储权限需独立保证。
业务明细去重不能仅按整行 hash；报告修订或字段排序变化后，仍需识别同一经济动作，避免重复消费。
零交易日也需要“范围完整且无数据”的可追溯证明；未到文件与空文件不是同一个状态。
报告晚到、分页期间数据更新、修订账单和银行流水晚入账均需要重新核对，保留旧运行结果及新水位。
完整性不足时可以给出“已获取范围内”的暂时结果，但不得计入全量核对通过或关闭未见记录差错。
原始报告与银行证据置于受控存储，公开仓库只保留字段说明和虚构示例，不暴露真实账户或交易数据。

## 9. 差错 owner、账龄与证据状态

| 差错类别 | 示例 | 默认责任角色 | 关闭前需要的证据 |
| --- | --- | --- | --- |
| 交易缺失或矛盾 | 内部失败但渠道已扣款 | 支付运营与渠道对接人 | 查询/报表结果、原操作收敛与必要入账 |
| 入账差错 | 错商户、漏凭证、重复费用 | 账务负责人 | 原凭证、审批、修正凭证及重算结果 |
| 批次差额 | 费用补扣、准备金释放遗漏 | 结算运营与财务 | 批次明细、合同及净额桥接 |
| 银行未匹配 | 在途未到账或收到不明款 | 资金运营与银行对接人 | 汇款参考、银行流水及归属确认 |
| 数据不完整 | 报表缺页、修订未获取 | 数据采集负责人 | 补齐来源、完整性核验与重跑记录 |

每张差错单必须有唯一 owner，协作方不能替代归口责任；保存差错金额、币种、影响主体与受限动作。
账龄分别记录经济事件时间、预期应到时间、首次发现时间与最近证据时间；重试或转派不得重置账龄。
证据状态可分为待采集、已采集未验证、已验证、相互矛盾；处理状态另分待认领、调查中、待外部、待修正、待复核、已关闭。
未决资金表示事实已知但仍在合同或银行处理链路；差错待查表示归属、金额或结果不明，两者应分别统计。
超出合同或银行承诺窗口的在途可升级为差错，但仍不能凭账龄断言失败或自动释放 UNKNOWN 预留。
关闭必须解释差额来源、附可验证证据并经独立复核；“手工标记成功”或“下次自然抵销”不构成证据。

## 10. 修账与审计闭环

先修复事实认定或规则缺陷，再按已批准政策追加修正凭证；不能为了报表相等而先改账后找理由。
补偿与冲正必须引用原始凭证，关联差错单、责任人、审批、修正范围和输入证据；journal/entry 不覆盖历史。
同一修账动作有唯一业务身份，重复审批回调或任务重放不能再次修账；部分修正须校验累计范围。
报告修订是新的证据版本，不等于有权删除旧报告、旧匹配关系或原出款；保留完整演进轨迹。
修账后重新核对受影响的四层、余额投影、商户应付和银行归属，不能只看待查科目余额归零。
会计期间关闭后按批准的跨期调整政策处理，并记录受影响报表；不得静默回写已封账历史。

## 11. 观测指标与待验证场景

| 指标 | 必须声明的口径 | 使用限制 |
| --- | --- | --- |
| 数据完整率 | 完整来源范围 / 预期来源范围，附截止时间 | 不把未收到报告记为零交易 |
| 逐笔与汇总匹配率 | 分层、分币种，分别统计条数与金额覆盖 | 净额抵销不能虚增逐笔匹配率 |
| 差错敞口与账龄 | 未解决金额、方向、币种、首次发现及应到日 | 不跨币种直接相加，不因转派重置 |
| UNKNOWN 存量与持续时间 | 按原操作追踪未决指令、对应占额和证据时点 | 自动释放预留不代表风险消失 |
| 出款及时性与流动性缺口 | 合同应付时点对比实际完成证据，区分资金不足原因 | 不把渠道受理时间当商户到账时间 |

指标阈值、告警等级和服务目标应由合同、业务体量、历史基线及风险承受能力确定；本文不编造数值阈值。
待验证场景：同批与跨批退款、重复文件、缺页、时区边界、修订报告、一对多银行流水和手续费补扣。
故障场景还应覆盖发送后丢响应、UNKNOWN 跨日、出款成功后退回、重复回调、修账重放及投影延迟。
验收应证明不重复付款、不错误释放、差额可解释、原历史可追溯；这里仅列计划，没有执行或达标声明。
