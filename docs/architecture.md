# 领域边界与架构决策

> 状态：参考设计，未实现。图与模块名称不代表已有服务、代码、团队或部署。设计基线：2026-10-30。

## 1. 设计问题

本项目关注一次商户收款如何在不可靠网络和异步外部机构中形成可解释的资金事实。可用性、低延迟和吞吐量重要，但不能通过丢弃未知结果、重复资金操作或修改历史账项获得。

核心问题不是“使用哪种队列”，而是：

- 哪个主体有权声明哪一种成功？
- 哪些数据需要共同提交，才能保持业务约束？
- 外部已经执行、内部尚未确认时如何恢复？
- 资金最终如何核对、结算和归还？

总体图见[项目首页](../README.md#核心架构)，详细图见[图集](diagrams/README.md)。

## 2. 参与方与资金边界

| 参与方 | 业务责任 | 不可直接假设 |
| --- | --- | --- |
| 付款方 | 提供支付授权，承担适用付款义务 | 前端跳转成功就等于资金完成 |
| 商户 | 提供商品或服务，提出收款及退款请求 | 商户订单与支付单永远一对一 |
| 支付编排平台 | 跟踪请求与渠道结果，维护操作身份 | 平台一定持有资金或拥有代收款 |
| 结算义务主体 | 按实际合同维护应付、费用与付款义务 | 纯技术网关可直接确认这些资产负债 |
| 渠道、收单机构等 | 按产品契约执行支付操作并提供结果 | 所有渠道的成功、撤销和退款语义相同 |
| 银行或托管机构 | 保存账户资金并提供划转、入账证据 | 渠道显示已结算就代表商户已到账 |
| 运营、财务、审计 | 处理差错、核对证据并审批敏感变更 | 有运营权限就可直接更改已入账余额 |

角色可以由同一机构承担，也可以拆分。实施前必须明确合同主体、资金所有权、客户资金隔离方式、地区及监管要求。

## 3. 三种事实分别归属

### 交易事实

支付编排拥有支付单、渠道尝试、资金操作、标准化结果与状态历史。渠道适配层提供结果证据，不能仅凭自身调用完成就宣布业务成功。

### 账务事实

账务模块拥有账户、凭证、分录、资金预留与余额约束。外部结果与入账完成是两个事实，允许短暂不一致但必须可追踪、可恢复、有门禁。

### 实际资金事实

资金模块拥有应结计算、批次、出款操作及到账核对。银行流水和渠道报表提供外部证据；对账模块保存匹配关系与差错，不反向直接覆盖源系统历史。

## 4. 逻辑模块与写入边界

| 模块 | 拥有的数据 | 输入 | 输出与限制 |
| --- | --- | --- | --- |
| 接入与权限 | 商户身份映射、操作授权上下文 | 已认证业务请求 | 可执行请求；不能改账 |
| 支付编排 | 支付单、尝试、操作、状态历史 | 业务指令、可信渠道结果 | 渠道任务、资金业务事件 |
| 渠道适配 | 原始协议证据、外部引用、能力配置 | 已持久化操作 | 标准化结果；保留原始语义 |
| 账务账户 | 账户、凭证、分录、预留、余额版本 | 经验证的经济事项 | 入账结果、余额与占用变化 |
| 清分计费 | 规则版本、明细归属、费用计算 | 适用交易及入账事实 | 应结结果；不是到账证明 |
| 结算出款 | 批次、明细、出款尝试 | 应结结果、资金和风险条件 | 出款任务、状态、资金事件 |
| 对账差错 | 文件完整性、匹配、差错、处理记录 | 内外部交易、账项和流水 | 匹配证据、补查及经审批的调整请求 |

部署在同一进程或同一数据库，不意味着任何模块都可以任意更新其他模块的表。模块所有权是维护业务约束的责任边界。

## 5. 关键对象与关联

- 业务订单：商品、服务或应收义务的业务载体。
- 支付单：明确金额、币种与收款目标；支持哪些拆分方式另行定义。
- 渠道尝试：某次渠道执行身份；网络重试复用这次身份。
- 资金操作：收款、捕获、撤销、退款、出款等各自的执行与额度约束。
- 凭证与分录：对经济事项的记账表达，不等于原始支付事件本身。
- 结算批次：一组满足相同结算口径的明细及其出款关联。
- 差错事项：内部记录与外部证据的不一致，包含独立处理状态。

必须保留商户、法人或账簿、业务操作、外部交易和记账凭证之间的关联。一个事件 ID 不足以替代这些业务身份。

业务支付单的成功不因退款被擦除；发生重复扣款时，也不能只保留“选中的那笔成功”而丢弃另一笔真实资金事实。

## 6. 同步、异步与批处理

| 路径 | 参考交互方式 | 成功边界 |
| --- | --- | --- |
| 接收支付请求 | 同步接受或返回现有操作 | 已可靠受理，不等于扣款完成 |
| 执行渠道操作 | 持久化任务驱动，可同步等待短结果 | 按具体资金操作契约判断 |
| 接收通知或查单结果 | 外部异步通知或主动查询 | 证据持久化并完成合法迁移 |
| 业务事实到记账 | Outbox至少一次投递，或明确同步调用 | 账务事务提交，不等于资金到账 |
| 清分与结算 | 按规则计算与周期处理 | 计算、出款、到账各自独立 |
| 对账 | 事件、文件或批次触发 | 资料完整、匹配成立或差错闭环 |

异步调用不意味着可以忽略顺序和幂等；同步调用也不意味着跨系统具备原子性。

## 7. 关键架构决策

### A01：采用显式状态，而非成功/失败二值模型

理由：结果丢失会导致本地知识不足。保留 UNKNOWN 和长期未决处理路径，避免把不确定性转化为重复扣款。

代价：客户端需要查询或订阅后续结果，运营需要处理未决账龄。

### A02：把幂等放在业务操作与记账凭证上

理由：消息可能重发，不同消息也可能描述同一业务结果。接口防重、渠道防重与账务防重各有作用域。

代价：需要参数绑定、唯一约束、保留策略及历史查询，不能只使用短期缓存。

### A03：优先定义本地原子边界

理由：业务状态与 Outbox、消费记录与账务效果应分别原子提交，不能把消息中间件保证当成外部资金保证。

代价：跨数据库或外部渠道仍有恢复窗口，必须持久化身份与证据。

### A04：后续实现先采用模块化单体

理由：在业务和验证尚未成熟时，先降低跨服务事务与运维成本。明确模块写入边界，便于未来按实际瓶颈拆分。

代价：需要持续防止模块之间直接改表；热点和故障隔离可能推动局部拆分。

这是未来实现建议，仓库当前没有任何单体或微服务实现，也未锁定语言、数据库和消息产品。

### A05：账务与结算独立表达

理由：资产负债确认、实际资金入账和商户出款不是同一个时间点。将余额与可结算额度混同会造成提前放款。

代价：必须管理中间科目、预留与资金条件，增加对账与流动性管理工作。

## 8. 不在本设计中假定的能力

- 不假定一个渠道支持无限期幂等、可靠撤销或即时查单可见。
- 不假定渠道交易、银行流水与内部凭证存在天然一对一关系。
- 不假定法律上允许平台持有、归集或自由使用客户资金。
- 不假定所有退款、拒付和部分捕获使用同一额度规则。
- 不声称异步复制、多活或分片能天然保证余额正确。
- 不给出未经测量的吞吐量、延迟、RPO、RTO或恢复时间承诺。

## 9. 落地前必须回答

1. 谁承担商户付款义务，谁实际持有资金？
2. 每种支付方式的授权、捕获和最终结果分别意味着什么？
3. 渠道请求身份、去重保留期、查单可见性及区域作用域是什么？
4. 业务履约、提现和结算分别依赖哪些已确认事实？
5. 哪些资金约束必须在同一个事务域中成立？
6. 历史证据、敏感数据和幂等记录分别保留多久？
7. 哪些异常可以自动恢复，哪些必须升级给有权限的人员？
